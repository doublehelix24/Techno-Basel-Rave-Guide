# Techno | Zürich | Basel After Dark

This repository is a static event guide hosted on Netlify. Netlify's publish directory is `public/` (also declared in `netlify.toml`). There is no build step or package manager. The deployable site consists of `public/index.html`, `public/guide.css`, `public/bunker.css`, `public/guide.js`, `public/techno-circle.png`, and the `public/venue-*` image assets; keep their relative paths working from `public/`.

## Editing the guide

- The permanent site name is “Techno | Zürich | Basel After Dark.” The title cycles through Techno, Zürich, and Basel; Basel is marked as upcoming. Techno Circle Basel is the guide's brand.
- The supplied logo PNG has a dark outer matte. The logo display in `public/guide.css` clips to the colored roundel so it looks clean on light backgrounds; preserve that treatment or use a transparent replacement.
- The page has OS-based dark mode with a saved manual override. Keep the mobile layout, keyboard access, and `prefers-reduced-motion` treatment when changing interactions or animation. Mobile navigation links and controls need at least 44px tap targets. Keep the mobile navigation a text menu without pill/button styling or horizontal scrolling; use two rows on narrow phones.
- The overview rows, event detail sections, venue comparison, comparisons, and source directory live in `public/index.html`. Keep the venue section after the event details. Calendar data lives in the ordered `events` array in `public/guide.js`; its order must match the overview rows. Each event needs a matching section ID and downloadable calendar invite. Keep “Save in calendar” in each event header beside the back-to-overview link. The overview has no separate jump links: its second column is “Artist / venue”, named events carry an `event-tag` in the “Musical identity” cell, and each date discloses its start and end times.
- Calendar times use `Europe/Zurich`, including overnight end dates. Verify schedules, venues, prices, and ticket links against primary event sources before changing facts. Taste and character scores are editorial. Group fit is calculated: the rounded average of an event’s three highest taste-fit scores. When taste scores change, update the group fit in the overview “Fit /10” cell, the event kicker and the “Trance, groove and setting” table on both pages. Keep the “Last updated” tag accurate when event research changes.
- Display every amount in the overview's “CHF (from)” column with exactly two decimal places, including whole-franc prices. Every “CHF (from)” price must link to the same ticket-sale URL used by that event's “Buy tickets” link in its detail section; for events with multiple ticket categories, keep the price link separate from the expandable category information.
- Each venue has a photo preview sourced from the actual venue or an official event partner, with a visible source credit. Prefer clear interior views showing the dancefloor, stage, gallery or room layout over performers, crowds or branding. Display the full image without cropping. Use a chevron-only expander with an accessible name and expansion state; overview popouts show “Details” to the left of “Website”, with the source credit shown separately. “Details” navigates to the same venue card as the overview venue-name link. Venue comparison photo cards expand and collapse together; following either venue-details link opens all cards. Keep the images in `public/`, only reveal them on hover or an explicit expansion, and distinguish Warehouse's pre-opening promotional image from a finished-venue photograph. Overview venue names link to the venue comparison and provide a touch/keyboard-accessible preview.
- The top-right version label and dialog are both in `public/index.html`. **Do not increment the version unless the user explicitly asks.** The current version is 3. The button shows only `v3` (or the current version counter); keep “Open changelog” in its accessible label or tooltip, not as visible button text. Keep the changelog as a cumulative record of meaningful user-facing additions and changes, ordered from biggest feature to smallest, with an emoji for each entry. Make it complete and readable rather than a token summary. Leave out implementation details, internal moves, and bug fixes. Keep the creator credit in the footer; the current wording is “Created with 🖤🎧 by Felix”. The footer uses “Techno | Basel | Zurich After Dark” with English city spelling.

## Implementation and prototypes

- `public/index.html` contains the base markup and an inline base stylesheet; `public/guide.css` loads afterward, then the Anton, Inter and JetBrains Mono web fonts and `public/bunker.css`. Check the cascade before adding overrides.
- The main design is Bunker, a black-concrete club-poster look promoted from prototype A. Its rules live in `public/bunker.css`, scoped to `<html data-design="bunker">`, with light and dark tokens that follow the device setting and the saved manual override; the nav stays dark in both themes. `public/guide.css` holds the shared base and the former main design, now the Club prototype. Style main-design changes in `public/bunker.css`, and check both themes. `public/guide.js` enhances the markup at runtime, including overview links, ticket prices, musical fit controls, venue previews, calendar buttons, themes and the version dialog.
- Event enhancement pairs overview rows with the `events` array by position and reads each detail section’s `.facts` and `.ratings` markup. Preserve those selectors and the `TICKETS` row label, or update the JavaScript together with the markup. Inspect the rendered page when checking generated links and controls. The overview filters, calendar view and event pop-up are generated by `public/guide.js`: genre filters use taste-fit scores of 7+/10, prices come from the overview’s “CHF (from)” cells, and the pop-up moves the real event section into a dialog and back, so keep event sections self-contained. Line-up artist menus read the `artists` map in `public/guide.js`; mark linked names with `<span class="artist">` and only add verified official profiles.
- The design explorer is `public/prototypes/index.html`, served at `/prototypes/`; select designs with `?variant=current`, `?variant=B` through `H`, or `?variant=I`. D and H lead the selector and cycling order; D opens by default. `current` is the main Bunker design (the switcher sets `data-design="bunker"` and loads `../bunker.css`); old `?variant=A` links open it. I is Club, the former main design, rendered with plain `../guide.css` and its own theme toggle. Variant names and switching live in `prototype-redesign.js`, C/D/E styles in `prototype-redesign.css`, and B/F/G/H styles in `prototype-new.css`. B is Pulse, F is Night Map, G is Sunset Radio, and H is Briefing, a light editorial report design with a matching dark theme; the former Gallery design has been replaced.
- The prototype HTML is a separate snapshot that shares `../guide.css`, `../bunker.css` and `../guide.js`. Keep design experiments scoped to prototype files unless the user requests adopting them in the main guide. For shared guide changes, check both pages and keep their event IDs, row order and required markup compatible with the shared script. Apply shared navigation, footer and version-label changes to both pages.
- Keep prototypes marked `noindex,nofollow`. Preserve `../` paths to shared assets and the prototype script’s handling of dynamically created venue images. The `current` option shows the snapshot with the main Bunker styling, not a live copy of the main HTML.
- Favor readable event information and usable controls when exploring new designs. Keep native keyboard behavior, visible focus, readable contrast and accessible previews. B/F/G/H support device themes and the saved manual override; preserve that behavior when editing them.

## Publishing and checks

- Netlify publishes `public/` directly from this repository. Put every site asset needed at runtime inside that folder; repository-root files are not served.
- Netlify's production branch is `live`, not `main`. Day-to-day work is committed to `main`, and pushing `main` does not change the live site. Each production deploy costs 15 of the free plan's 300 monthly Netlify credits, so batch changes into few releases; deploy previews, branch deploys, failed deploys and rollbacks are free.
- For browser previews, serve `public/` directly (for example, `python3 -m http.server 8000 --directory public`). Preview the affected pages at desktop and phone widths after visual changes; use 320px and 390px phone widths to catch overflow and navigation regressions. Check edited prototype variants as well as the main guide when shared files change. Check the animated title/tagline, Zürich's umlaut, the overview links and fit controls, dark mode, and a sample Zürich-time calendar invite when related code changes.
- Run checks proportionate to the change: use `git diff --check`, `node --check` for edited JavaScript, and browser checks for affected layouts or interactions. There is no build or package-install step. Do not depend on temporary `/tmp` scripts from earlier sessions being available.
- Commit completed changes. Never push automatically; push to the Git remote only when the user explicitly asks. A one-time push request authorizes that batch of work, not subsequent changes.
- “Push” means `git push origin main` only; it does not publish the site. “Push live”, “go live”, “publish” or “deploy” means releasing `main` to production: commit the work, push `main`, fast-forward `live` to `main` (`git push origin main:live`; never force-push `live`), then confirm the Netlify deployment status. One go-live request authorizes one release. Report a successful Git push separately from a verified Netlify deployment; absent GitHub deployment checks do not establish that the site is live. To undo a bad release, prefer Netlify's free rollback over a new deploy.
